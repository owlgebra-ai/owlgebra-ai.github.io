o-means release report

File paths in this document refer to the project’s working repository.

Date: 2026-11-12. Release: omeans.v2 (entry omeans.v2:R4C), code at main 9c2a281. Reference: e-means (arXiv 2611.09501, faiss contrib/e_means snapshot 7767c63). Protocol: evals/PROTOCOL.md v1, locked in evals/LOCK.json. Every number below is a line in results/ledger.jsonl.

Result

On the held-out test suite o-means reaches e-means’ quality in about 1/4.5 of the wall-clock time, and its quality at equal time is not worse. The test suite was run once on the release candidate (ledger round 50); no test data was used for tuning and there were no re-runs.

The @5 column is unscored for a reason: time-to-e-means@5 is unstable even for an identical algorithm (PROTOCOL §8), and on dev-full six (config, seed) pairs never reached it within the ladder.

Systems vs algorithm (PROTOCOL §7b)

e-means cannot use its H100-only kernels on the RTX 5090, so part of any win is implementation. omeans.v0 is e-means’ algorithm on o-means’ fused FP16 kernels; it uses the same number of distance evaluations as e-means or more (ratio 1.0–1.33 at the crossings), so its gain is kernels only.

How o-means differs from e-means

Unchanged: the objective, the starting centroids, the EMA mini-batch update, the batch-size law and split-based revival of dead clusters.

  1. Two-level assignment (omeans/kernels/twolevel.py, omeans/v2/loop.py). Centroids are grouped into G = round_up(k/128, 16) coarse cells. Each point picks its p nearest cells (p = 16 for d < 512, 12 for d ≥ 512, 24 for k > 16,384) and is compared only with the centroids in those cells: three kernel launches per batch (coarse pick and bucketing, fine distances, reduce). Cells are rebuilt after every revival check in the first pass, then every half pass; children of split centroids are checked explicitly so points do not miss them between rebuilds.
  2. Closing mean. Below 2 epochs the final centroids are a split-aware, recency-weighted one-pass mean ("window" close) instead of e-means’ last-pass mean: −0.36 to −0.70% MSE at 1 epoch (docs/design/d1-results.md). From 2 epochs up it is e-means’ closing mean.
  3. Kernels. Fused FP16 Triton kernels for the dense passes (v0).
  4. Effort ladder [0.8, 1, 1.6, 2, 2.5, 3.2, 4, 5, 8, 12.8] epochs.

Checks

  • Independent audit of the candidate against PROTOCOL §7: no cross-call state, nothing outside the timer, no access to eval rows in the fit path, no branching on dataset identity.
  • Synthetic unseen shapes (docs/design/r4-shapes.md, 39 fits): peak memory at most 14.6 GB; nearest-centroid miss rate 0.004–1.06% on 10M-row shapes.
  • Noise floor: identical-algorithm controls scored within 0.013 of 1.0 on dev-fast.

Limitations

  • One machine. All speedups are on one RTX 5090, where e-means runs its Triton backend. On an H100 with e-means’ CuTe kernels the systems part (about 1.4–1.5×) would likely shrink. The distance-evaluation ratios (0.06–0.30) show the algorithm does less arithmetic, but roughly 7× fewer evaluations bought about 3× in time on this card; whether that exchange rate holds on other hardware is unmeasured.
  • The probe rule is fitted on few datasets. On real development data 0.5–2.4% of points miss their nearest centroid; on GloVe-200 (cosine-like data) it is 4–13% at p = 16, costing about 0.1% MSE. (The 0.004–1.06% figure under Checks is for synthetic 10M-row shapes only.) An adaptive variant (R4P) that measures misses in-fit and raises p exists as a fallback; it was not chosen because it costs 2–4% time on well-behaved data.
  • Hub cells. On synthetic, well-separated high-dimensional mixtures a few coarse cells hold most centroids and the speedup disappears (quality is unaffected). Not seen on real datasets in any suite.
  • Small k. The three lowest per-dataset speedups are the three k = 8,192 configs (SimpleWiki, CC-News, CelebA): with only 64 coarse cells the two-level structure saves less.
  • Ladder placement is worth about 4% of the score, and two top ladder steps (5 → 8, 8 → 12.8) exceed the 1.6× interpolation limit on some shapes; that affects only the unscored @5 column and gap5.
  • Approximate assignment. The returned centroids come from approximate nearest-centroid assignment during training. Quality is scored with exact assignment and is not worse than e-means’ at e-means’ 5-epoch time on any of the 17 real configs (dev-full and test), but there is no worst-case guarantee.
  • Scope. GPU track only; no CPU implementation. 3–5 seeds per config instead of the paper’s 10; per-seed starts follow the paper’s recipe but not its exact permutations. No 100M or 1B configs. Targets are e-means at 1–3 epochs rather than the paper’s Lloyd@25 anchor (PROTOCOL §8).

Reproduce

On the GPU box, from the project directory, at commit 9c2a281 or later:

python -m evals.run_suite --suite dev-full --variant my-check --candidate omeans.v2

python -m evals.aggregate --suite dev-full --variant my-check --json /tmp/agg.json

The test suite additionally needs --release; every test run is recorded in the ledger. Use as a library: from omeans.v2 import fit; centroids, info = fit(x, k, init, effort, seed) with x and init as float32 CUDA tensors.
